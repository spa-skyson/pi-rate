# Дизайн v2: фоновые сессии для pi-rate TUI (issue #74)

Статус: предложено. Основа: v1-фон (`internal/tui/background.go`, !44), research
opencode v2.0.28 (комментарий в issue #74 от 2026-10-13). Код не пишем — это
контракт для реализации.

Главная жалоба, которую закрываем: после Ctrl+B сообщение pm-агенту встаёт в
очередь фонового рана вместо мгновенного ответа. Причина — v1 освобождает
*ввод*, но не *агента*: ран остаётся на главном `*Agent`, и все guard'ы
(`startAgentLoop`, `applyAgent`, `startNextPrompt`) честно отказывают.

---

## 1. Целевая модель: сессия-слот

**Решение: ран при Ctrl+B остаётся в той же сессии; фоновой становится текущая
сессия целиком; активный слот открывает новую пустую. Миграции рана нет.**

Что такое сессия в терминах кода — `sessionSlot`:

```
sessionSlot {
    id        string            // ADK sessionID; events.jsonl уже пер-сессионный
    agent     *agent.Agent      // свой экземпляр; заморожен, пока в слоте жив луп
    transcript []message        // m.chatModel.Messages этого слота (+ TraceLog)
    inbox     []queuedPrompt    // бывшие m.pendingPrompts
    buf       []agentMsg        // v1 bg-буфер: хвост событий при фоне
    approval/question stash     // v1-стэш запросов ввода
    state     enum              // busy | attention | idle-unread | idle | dead
    started/finished, unread    // watermarks для бейджей
}

model {
    slots   []*sessionSlot      // реестр: [0] — активный, остальные — фоновые
    // m.chatModel/m.pendingPrompts/m.bg становятся проекциями активного слота
}
```

Жизненный цикл: слот рождается при Ctrl+B из живой сессии (её состояние
*переезжает* в слот) или командой `/new` (пустой слот). Умирает — при выходе из
TUI или закрытии из попапа (при живом ране — только с cancel, как
`cancelBackgroundRun`).

**Оценка альтернативы «ран мигрирует в новую сессию»** — отклонена:
`runAgentLoop` пишет события в `events.jsonl` по `run.sessionID` через ADK
runner; миграция = re-parenting файла на лету и подмена sessionID внутри живого
раннера — ADK этого API не даёт, и транскрипт на экране уже принадлежит той
сессии. У opencode сессия тоже не мигрирует — переключаются «просто так»; наш
detach — момент ветвления активного слота, не рана.

Важное следствие: durable-транскрипт фона уже работает. Ран сам персистит
граничные события в `events.jsonl` независимо от TUI-рендеринга (FileService
дропает партиалы). Буфер слота — не источник истины, а хвост для структурного
реплея при attach и для TUI-only событий (warnings), которых нет в
events.jsonl. `restoreTranscript` (session_restore.go) — уже готовый запасной
путь реплея при переполнении буфера.

## 2. Агент-объекты: один `*Agent` на сессию

**Решение: per-session `*Agent`, строительство через фабрику; общий только
`SessionService` (FileService) и общие инстансы тулзов.**

Обоснование из research: инструкция и модель — *данные сессии*, а не процесса.
Shared-агент не спасает даже снапшотом раннера на старте тура: следующий промпт
из очереди фоновой сессии прочитал бы уже чужую инструкцию после переключения
активного слота на pm. Per-session агент убирает `RebuildWithSession`-гонку *по
построению*: мутации подвергается только агент слота, и только когда в его
слоте нет живого лупа. `RebuildWithSession` переиспользуется без правок — как
сегодня в `applyAgent`, но на агенте слота.

Стоимость допустима: `agent.New` дёшев (runner = LLM + ссылки на уже
построенные тулзы; MCP-коннекты и оркестратор не пересоздаются). Per-сессионными
делаются только замыкания, которым нужен sessionID: approval-asker и
question-bridge (см. §6).

Контракт фабрики (новое поле `tui.Config`):

```go
// NewSessionAgent строит агента для новой сессии: CreateSession + agent.New на
// базовом конфиге, с per-сессионными asker-замыканиями и установленным
// preTurn-хуком (autocompact). CLI повторно использует код строительства
// стартового агента, параметризованный sessionID.
NewSessionAgent func(ctx context.Context) (ag *agent.Agent, sessionID, title string, err error)
```

Прецедент в коде: `plan.go:442` уже создаёт новую сессию внутри TUI и
подменяет `m.cfg.SessionID` — фабрика легализует этот путь.

`m.cfg.Agent`/`m.cfg.SessionID` остаются указателями на *активный* слот (их
читают команды); правило: запись — только через swap активного слота.

## 3. Шина событий: конверты по слоту

**Решение: обобщение `bgEnvelope` до `slotEnvelope{slot, ev}`; один паркованный
читатель на канал — инвариант v1 сохраняется дословно, на каждый канал.**

Разрез минимальный, три правила:

1. **Читатель.** Канал рана (`agentCh`, создаётся в `startAgentLoop`) имеет
   ровно одного паркованного читателя; при фоне он ре-армится в
   `slotEnvelope{slot, ...}` (сегодня `waitForBgAgent` → `waitForSlotAgent`).
   Классификация по *каналу*, не по указателю — v1-правило (background.go:305)
   переносится как есть.
2. **Роутинг.** `updateAgentStream` первым делом разворачивает
   `slotEnvelope`: слот активный → обычные хендлеры + обычный ре-арм; слот
   фоновый → `slot.record(ev)` + агрегатор статуса (бейдж тикает), ре-арм в
   конверт. Дельты рендерит только активный слот.
3. **Финал.** `agentDoneMsg` из фонового слота идёт в *слотовый* close-out
   (§6/§7), не в `handleAgentDone` активного. v1-ветка `bgAlive` в
   `updateAgentStream` умирает — её работу делает конверт.

Сайдбенд-каналы (ApprovalCh, QuestionCh, AgentEventCh) — глобальные; у каждого
тоже один паркованный читатель, но сообщения несут тег сессии (§6). Это и есть
«шина»: один канал на источник, роутинг по слоту в конверте/теге,
replay-then-live на attach. Никакого отдельного брокера.

## 4. Inbox: пер-сессионный

**Решение: `pendingPrompts` переезжает в слот; ввод всегда идёт в активный
слот; «в другую сессию» — только через её inbox, не через глобальную очередь.**

- Ввод в активный слот, слот занят → очередь *его* inbox (как сегодня).
- Промпт в фоновую сессию (MR3, из попапа) → enqueue в её inbox.
- Автопродвижение: фоновая сессия, чей ран закончился, сама стартует следующий
  промпт из своего inbox (v1 уже разрешал это: `finishBackgroundRun` →
  `handleAgentDone` → `startNextPrompt`; теперь то же пер-сессионно). Глобальная
  очередь исчезает вместе с guard'ом `bgAlive` в `startNextPrompt`.
- При detach неотработанные промпты очереди уезжают вместе со слотом — они
  принадлежали тому разговору.

## 5. UI

- **Реестр**: попап по образцу search-popup (`overlaySessions` в стек оверлеев):
  список слотов — title, агент, статус (busy/⚑/idle-unread), elapsed, events.
  Выбор = переключение; на неактивном слоте — действия (attach / cancel / send
  prompt в MR3). Вызов: `/sessions` + клавиша (предложение `Ctrl+O`;
  финальный биндинг — UX-решение, не архитектурное).
- **Статус-бар**: бейджи фоновых слотов — `[⚡pm 2:14]` busy, `[⚑]` ждёт ответа,
  `[✉2]` idle-unread (watermark: события после последнего attach). Заменяет
  v1-строку `BackgroundStatus` одним агрегатором.
- **Ctrl+B**: нет фона → detach; один фоновый → attach; много → попап.
- **Attach** = swap активного слота (текущий активный при живом ране сам
  становится фоновым — рекурсия detach, начиная с MR2) + перенос transcript
  обратно + структурный реплей буфера через существующие хендлеры (v1-механика
  `replayAgentEvent` целиком). `replayBackgroundDigest` **удаляется**: дайджест
  существовал из-за общего транскрипта, теперь транскрипты раздельны и задача
  исчезает. Буфер остаётся (реплей + warnings); при `dropped > 0` — fallback на
  `restoreTranscript` из events.jsonl.

## 6. Диалоги из фона: тег сессии + стэш

**Решение: все кросс-сессионные сообщения несут тег; фоновый запрос паркуется в
стэш слота с ⚑-бейджем; ответ — только из своего слота.**

Проблема v1: ApprovalCh/QuestionCh глобальны, `ApprovalRequest`/`QuestionRequest`
не несут сессии. При одном ране это невидимо; при двух живых ранах запросы
неразличимы — маршрут «первый попавшийся» отвечает чужому рану.

Механизм тега — per-агентное замыкание при строительстве (никакой магии ctx):

```go
// interactive.go: asker строится на агент с уже известным sessionID
approvalAsker(ch, sessionID) // req.SessionID = sessionID — поле добавляется
```

- Активному слоту — диалог как обычно; фоновому — v1-стэш (`handleBackground
  Approval/Question` на слоте) + attention (bell/OSC 777) + ⚑.
- Fail-closed пути (уже есть в v1, переносятся): смерть рана → denied; второй
  запрос в том же слоте → первый denied; **новое**: запрос с пустым тегом —
  deny + запись в лог (это баг фабрики, не пользовательский сценарий).
- `AgentSubEvent` получает `ParentSessionID` ( MR2): тег прошивается в месте
  spawn'а (тул-колл исполняется в ране родителя; оркестратор ведёт карту
  agentID→session). До этого — субагентские события фоновых слотов идут только
  в монитор, не в их буферы (v1-поведение `waitForSubEvent`-ре-арма сохраняется).

## 7. Close-out и инвариант AGENTS.md

`handleAgentDone` сегодня — глобальный финализатор: трогает `m.running`,
диалоги, `m.mode=="plan"` + worktree-финализацию, очередь, fallback-модель. При
фоне в *чужой* сессии это контаминация активного слота. Разрез:

- `finishSlotRun(slot, done)` — слотовая часть: done-флаг, стэш → denied,
  notice в транскрипт слота, watermark/unread, терминальное attention-событие,
  автостарт своего inbox.
- `handleAgentDone` — остаётся финализатором *активного* слота (вызывает
  слотовую часть + то, что по природе глобально: тики, attention).
- Правило: финал рана никогда не пишет в состояние другого слота; глобальные
  поверхности (статус-бар, attention) обновляются только через агрегатор.

Непереключаемые окна (документированные исключения): `/run`-цикл (события идут
мимо agentCh — v1-отказ сохраняется) и окно plan-финализации (planWorktree —
глобальные поля модели; пока plan-состояние не слотовое — refuse detach).
Отказ именует причину, как сегодня.

## 8. Схема потоков

```
                 ┌────────────────────────── TUI (Update, один поток) ──────────────────────────┐
                 │                                                                                   │
  ввод ──────────► активный слот: занят? → inbox активного : startAgentLoop (луп активного слота)  │
                 │                                                                                   │
                 │  слот[0]=активный          слот[1..N]=фоновые: agent+transcript+inbox+buf+stash  │
                 │       │                                                                 │         │
                 │   waitForAgent(ch₀)───conверт slotEnvelope{slot,ev}───── waitForSlotAgent(chᵢ)  │
                 │       │                         │                                           │
                 │  дельты → рендер          слот активный? ──да──► обычные хендлеры (live-join)  │
                 │  (транскрипт активного)        │нет                                           │
                 │                          buf слота + агрегатор бейджей; done → finishSlotRun   │
                 │                                                                                   │
                 │  ApprovalCh/QuestionCh (тег SessionID): активный → диалог; фон → стэш+⚑         │
                 │  AgentEventCh (ParentSessionID, MR2): свой слот / монитор                        │
                 └───────────────────────────────────────────────────────────────────────────────┘
   персистентность: каждый ран пишет в свой events.jsonl через SessionService (уже так);
                    TUI-рендеринг не участвует → фон durable по построению

Ctrl+B (ран активного):  слот активного ── всё состояние переезжает ──► новый фоновый слот
                         фабрика NewSessionAgent ──► свежий активный слот (пустой транскрипт)
Attach:                  swap слотов + transcript обратно + структурный реплей buf (v1-механика)
```

## 9. Инкрементальный план MR

Ответ на ключевой вопрос плана: **первый MR возможен как «fork без полной
шины», но с тремя неустранимыми элементами**: (а) тег сессии на
approval/question (иначе два одновременных рана путают диалоги), (б) слотовый
close-out фонового финала (иначе `handleAgentDone` ломает активный слот), (в)
перенос владения (транскрипт/inbox/agent) при detach. Полная шина — N слотов,
конверты, попап — MR2. Попытка сделать MR1 без (а)-(в) даёт случайную пару
запросов к разным ранам и финал фона, роняющий чужой тур.

| # | Скоуп | Ценность без следующих | Ключевые риски | Зависит |
|---|---|---|---|---|
| MR1 «fork-on-detach» | `backgroundRun` += sessionID/agent/transcript/inbox; detach = перенос владения + `NewSessionAgent` для активного; `ApprovalRequest`/`QuestionRequest` += `SessionID` + per-агентные asker-замыкания; `finishSlotRun` для фона; срыв guard'ов `bgAlive` в `startAgentLoop`/`startNextPrompt`/`applyAgent`/`handleRetry`/slash-гейте (остаётся только `m.running` активного); максимум ОДИН фоновый слот; attach при живом активном ране — refuse (вместо дайджеста) | Жалоба issue закрыта: Ctrl+B → pm отвечает мгновенно, слэш-команды работают | Двойная блокировка approval (тест с двумя гейтами); план/run-окна (refuse detach); потеря v1-дайджеста — поменянная семантика attach | — |
| MR2 «реестр» | `[]*sessionSlot` + active-указатель; `bgEnvelope` → `slotEnvelope`; роутинг в `updateAgentStream` по слоту; переключение всегда паркует активный (attach при живом ране = активный становится фоновым); попап `overlaySessions` + `/sessions` + `/new`; бейджи статус-бара (агрегатор); пер-слотовые `modelFallbacks`/`agentModelOverrides`/`mode`; `AgentSubEvent.ParentSessionID`. **Статус: частично реализовано** — реестр, канальная маршрутизация, попап (`/slots`, Ctrl+B при N>1), `/new`, агрегатор-бейджи готовы; паркинг-attach при живом ране, `ParentSessionID` и пер-слотовые `modelFallbacks`/`mode` перенесены в следующий инкремент (attach при живом ране отказывает — фактическая модель и её инварианты в AGENTS.md) | N параллельных фоновых задач, видимость, переключение в любой момент | Гонки на общих полях model при N лупах (снимок `agentRun()` при старте каждого лупа — правило «луп не читает m»); атрибуция субагентов | MR1 |
| MR3 «inbox/watermarks» | Промпт в фоновую из попапа (enqueue в её inbox); unread-счётчики/watermarks; refresh context-gauge при attach (`EstimateTokens`, паттерн `restoreSession`); настройка терминальных attention-событий per-слот | opencode-уровень inbox-UX | низкие | MR2 |
| MR4 «инварианты и чистка» | AGENTS.md (новая формулировка §ниже); удаление мёртвых v1-путей (`replayBackgroundDigest`, остатки `bgAlive`); генерализация guard-тестов (бюджет шагов/midturn — уже пер-лупные; добавить пер-слотовые); эпилог выхода со списком сессий | Долговечность: инварианты закреплены, мёртвый код удалён | низкие | MR2 (можно параллельно MR3) |

Порядок MR1 → MR2 → MR3, MR4 замыкает. Каждый MR зелёный сам по себе: MR1 не
трогает механизм конвертов (один фон — v1-механика на расширенной структуре),
MR2 не меняет семантику inbox, MR3 — чистая надстройка.

## 10. Новые инварианты для AGENTS.md (замена пункта turn-loop)

1. **Один живой луп на слот.** В слоте не более одного живого main-лупа;
   агент слота (`RebuildWithSession`/`RebuildWithModel`) мутируется только при
   отсутствии живого лупа *в его* слоте. Кросс-слотовых мутаций агента нет.
2. **Читатель никогда не меняет владельца — на каждый канал.** У канала рана и
   каждого сайдбенд-канала ровно один паркованный читатель, ре-арм по источнику
   сообщения. Конверт именует слот; классификация по каналу, не по указателю
   (v1-правило, обобщённое).
3. **Кросс-сессионное сообщение несёт тег.** `ApprovalRequest.SessionID`,
   `QuestionRequest.SessionID`, `AgentSubEvent.ParentSessionID`. Сообщение без
   тега — баг; роутинг никогда не угадывает «кто сейчас_running».
4. **Финал рана слотовый.** Завершение пишет только в состояние своего слота
   (диалоги, очередь, режим, транскрипт); глобальные поверхности — через
   агрегатор. Смерть рана закрывает его диалоги denied (dead-turn rule, per-slot).
5. **Detach переносит владение, не копирует.** Транскрипт, inbox, агент и
   sessionID переезжают в слот; активный слот рождается пустым. Дельты не
   пересекают слоты.
6. **Отказ именует слот.** Глобальных «фон активен»-отказов нет; guard защищает
   конкретный слот (`m.running` активного). Документированные исключения:
   `/run`-цикл и окно plan-финализации непереключаемы.
7. **Durability — рана, не рендера.** events.jsonl пишет ран через
   SessionService независимо от TUI; буфер слота — хвост реплея, не истина.

## 11. Топ-3 риска и митигация

1. **Маршрутизация approval/question при двух живых ранах.** Самый вероятный
   баговый класс: untagged-запрос уходит чужому рану, denied-ответ ломает
   невинный тур. Митигация: тег по per-агентному замыканию на фабрике;
   acceptance-тест MR1 — два гейта блокируют одновременно, каждый диалог
   отвечает своему рану; untagged → deny + лог.
2. **Контаминация close-out.** `handleAgentDone` трогает глобалы
   (`m.running`, `m.mode`, planWorktree, очередь). Фоновый финиш во время
   активного рана обязан не заметиться в активном слоте. Митигация:
   `finishSlotRun` как единственный путь фонового финала; acceptance-тест MR1 —
   фон завершается посреди активного рана, состояние активного слота
   неизменно.
3. **Гонки общих полей model при N лупах.** Лупы читают `m.cfg` — v1 решено
   снимком `agentRun()` при старте; новые поля должны следовать тому же
   правилу. Митигация: правило «луп не читает m» в AGENTS.md; аудит новых полей
   в ревью MR2; race-детектор в CI уже есть.

## Открытые вопросы (не блокируют MR1)

- Биндинг открытия реестра (`Ctrl+O`? — UX-решение).
